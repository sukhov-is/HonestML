# HonestML Audit Loop — контракт одного раунда (read-only аудит)

Это **один раунд** аудит-петли. Ты стартуешь со **свежим контекстом** — твоя память это файлы
на диске и git-история. Прочитай состояние, проведи **один аудит-проход под одной линзой**,
запиши подтверждённые находки, закоммить, выйди. Следующий раунд запускается заново.

**Назначение петли:** защитный аудит собственной кодовой базы — находить дефекты и слабые места,
пока они находятся, чтобы команда затем их устранила. **Сама петля ничего не исправляет.**

**Это ручной протокол: драйверы петли его не исполняют.** Раунды запускает человек, по одному,
в основной рабочей копии и **только при остановленной dev-петле**. Аудируется текущий HEAD; sha
фиксируется в строке раунда. Машинная альтернатива с теми же направлениями — скил `project-audit`.

---

## Жёсткие границы (важнее всего остального)

- **Read-only по отношению к проекту.** Писать/менять можно ТОЛЬКО файлы под `docs/audit/loop/`
  и файл `docs/audit/loop/DONE` (при завершении). Никаких правок `src/`, `tests/`, `benchmarks/`,
  `ops/`, `notebooks/`, `pyproject.toml`, прочих `docs/` — даже очевидных однострочных фиксов.
  Находка = запись в реестре.
- **Ремедиационная рамка.** Каждая находка формулируется как: какое свойство кода/системы нарушено,
  при каких условиях это проявляется, в каком направлении устранять. Пошаговые инструкции
  эксплуатации не нужны и не пишутся — адресат реестра это разработчик, чинящий свой код.
- **Не запускай** установку зависимостей и тяжёлые гейты (`uv run pytest`, `uv run mypy src`) —
  анализ статический (чтение кода/доков, grep, git log). Быстрые read-only команды
  (`uv run ruff check src tests`, `uv run lint-imports`, `git log/diff`) допустимы.
  Инструменты: чтение, поиск, read-only оболочка и параллельные субагенты.
- **Не вызывай скилы** (architecture-design/implementation/project-audit) — протокол раунда
  самодостаточен и описан ниже.
- Не трогай `docs/loop/state.md` (гроссбух dev-петли) — у аудит-петли свой гроссбух.

## 0. Ориентация (дёшево, сначала)

1. Если существует `docs/audit/loop/DONE` — аудит-пакет уже закрыт: немедленно выйди, ничего не делая.
2. Нет каталога `docs/audit/loop/` — заведи его регистры: `state.md` (шапка и пустая таблица раундов,
   колонки §6) и `findings.md` (шапка с форматом: основная таблица confirmed, секция rejected — §3).
   Дальше раунд идёт обычным ходом, линза первая.
3. Прочитай `docs/audit/loop/state.md` (гроссбух аудита: какая линза следующая, dry-серия)
   и `docs/audit/loop/findings.md` — секции реестра под линзу раунда плюс ключи дедупа (файл + суть)
   всех его строк: confirmed, rejected и tracked-отброшенные.
4. Корпус задают `docs/audit/profile.md` (стек, критичные пути, исключения из универсума файлов)
   и `docs/audit/learnings.md` (паттерны, подтверждённые владельцем как намеренные, — не флагать
   повторно). Читай их адресно под линзу раунда.
5. Проверь условие остановки (§4). Выполнено → финальный раунд (§5).

## 1. Выбор линзы

Ротация фиксированная; бери следующую после линзы последнего раунда в гроссбухе:

1. `security` — защитный аудит обращения с чувствительным: секреты в коде/логах/коммитах,
   десериализация недоверенных артефактов (joblib/pickle в `serializers.py`, `candidate_cache.py`,
   `artifact.py` — загрузка чужой модели равна выполнению кода), целостность и версия артефакта,
   валидация входа на границе Reader (CSV/parquet/DataFrame: схема, типы, размер), пути записи
   артефактов и кэша, устойчивость к некорректному/враждебному входу. Находка = нарушенное защитное
   свойство + условие проявления + направление устранения (см. «Ремедиационная рамка»).
2. `correctness` — корректность и полнота: соответствие кода заявленным требованиям
   (`docs/architecture/*/01-requirements/`, `docs/architecture/*/06-traceability.md`), честность
   оценки как fail-closed (утечка таргета в CV: purge/embargo, group-disjoint сплиты, кросс-фитовый
   таргет-энкодинг, ранжирование признаков на fit⊕es, калибровка на OOF, honest holdout),
   ориентация метрики (`greater_is_better` и знак), краевые случаи, off-by-one, обработка None/NaN
   и дрейф dtype, детерминизм прогона по сиду.
3. `performance` — горячие пути: лишние копии и материализации DataFrame (pandas↔polars), повторные
   fit'ы и пересчёты по фолдам, O(n²) на росте числа кандидатов/фолдов/признаков, утечки
   (незакрытые ресурсы), соблюдение `RunBudget`/`memory_limit_mb`, промахи кэша кандидатов.
4. `architecture` — слои и зависимости: дрейф от заявленной Clean Architecture
   (`core ← adapters ← application ← composition`), дыры в контрактах `.importlinter` (что НЕ покрыто
   тремя контрактами), циклы понятий, протекание фрейм- и ML-библиотек в `honestml.core`,
   дублирующиеся абстракции, God-модули.
5. `hygiene` — чистота: дублирование логики (copy-paste между модулями), мёртвый код, неиспользуемые
   экспорты/поля VO, противоречивые конвенции именования, тесты-тавтологии (проверяют реализацию, а не поведение).
6. `docs-drift` — код↔документация: расхождения `docs/adr/`, дизайн-пакетов `docs/architecture/<пакет>/`,
   гайдов (`docs/guide/`, `docs/api.md`, `docs/quickstart.md`), README и `CHANGELOG.md` с реальным кодом,
   устаревшие «Проверка»-колонки в `06-traceability.md`, битые пути/ссылки, заявленное-но-не-реализованное
   без пометки.
7. `wip-debt` — незавершёнка: TODO/FIXME/заглушки/NotImplementedError, мёртвые feature-флаги,
   dark-launch флаги без плана включения, «времянки», отключённые тесты, пустые except-ветки.

После того как ВСЕ 7 линз прошли ≥1 раз, ротация продолжается по тому же кругу, но каждый раунд
дополнительно (одним из субагентов) гоняй **completeness-критика**: «что этот аудит ещё ни разу
не проверял?» — его идеи расширяют задание линзы следующего раунда (фиксируй в note гроссбуха).

## 2. Аудит-проход (fan-out)

- Запусти **3–6 параллельных read-only субагентов**, отправленных одним сообщением, разрезав кодовую базу
  по зонам: `src/honestml/core`+`.importlinter`; `src/honestml/adapters` двумя кластерами (данные и
  артефакты: reader+loader+polars_dataset+serializers+candidate_cache+dtype_tokens; модели и оценка:
  estimators+boosting+splitters+metrics+significance+calibration+ensembling+feature_rankers+
  feature_selectors+tuning+onnx_export+run_budget+tracking);
  `src/honestml/application`+`src/honestml/composition`;
  `tests/`; `benchmarks/`+`ops/`+`scripts/`; `docs/`+`notebooks/` (для docs-drift).
  Зоны, нерелевантные линзе, пропускай.
- Каждому субагенту передай: линзу с конкретным чек-листом (§1), его зону (пути), рамку (защитный
  аудит для устранения) и формат ответа: `file:line · суть дефекта · severity (Critical/High/Medium/Low/Info) ·
  для correctness — сценарий отказа; для security — нарушенное свойство и условие проявления`.
  Субагент читает код сам; web не использует.
- **Шум-фильтр:** задокументированная незавершёнка — НЕ находка. Перед записью сверь кандидата с
  `docs/audit/learnings.md`, реестром последнего пакета `docs/audit/<дата>/02-ledger.md`,
  `docs/loop/backlog.md` («Осознанные исключения» и «Отложено (⏸ решение, дата)»),
  `docs/backlog.md`, `docs/implementation/changelog.md` и трассировками дизайн-пакетов: если
  «дефект» — это известный отложенный follow-up или принятый as-is компромисс с трекингом,
  отбрасывай (это `tracked`, не пиши в реестр).
  Находка = то, что НЕ трекается, противоречит заявленному или трекается неверно.

## 3. Дедуп и адверсариальная верификация

- **Дедуп против ВСЕГО реестра** (confirmed И rejected, И tracked-отброшенных прошлых раундов —
  они тоже в findings.md): ключ = файл + суть. Совпадение → кандидат отброшен молча.
- Каждого **нового** кандидата severity High+ верифицируй **слепым** субагентом: передай только
  файл(ы) и формулировку находки, БЕЗ своих выводов, с заданием «опровергни: докажи, что заявленное
  свойство на самом деле не нарушено или что условие проявления недостижимо». Не смог опровергнуть →
  `confirmed`; опроверг → `rejected` (с одной строкой почему). Low/Info подтверждай собственной
  перепроверкой кода (без субагента).
- В реестр `docs/audit/loop/findings.md` пиши ОБЕ категории (confirmed — в основную таблицу,
  rejected — в свою секцию одной строкой): rejected нужны дедупу, иначе петля не сойдётся.

## 4. Условие остановки (loop-until-dry)

Петля «суха», когда выполнены ОБА условия:
1. Каждая из 7 линз отработала **≥1 полный раунд**.
2. Последние **3 раунда подряд** дали `confirmed = 0` новых находок.

Проверяется в §0 по гроссбуху. Не выполнено → обычный раунд. Выполнено → §5.

## 5. Финальный раунд (только при выполнении §4)

1. Напиши `docs/audit/loop/SUMMARY.md`: диапазон аудированных HEAD (первый→последний sha),
   число раундов, сводка находок по severity и линзам, топ-10 приоритетных с рекомендацией
   «что чинить первым», перечень rejected (одной строкой каждая) и явные не-покрытые зоны (если остались).
2. Создай файл `docs/audit/loop/DONE` с текстом `audit loop dry: <N> rounds, <K> confirmed findings`.
   Рабочую петлю он не трогает.
3. Гроссбух + коммит (§6), выйди.

## 6. Гроссбух + коммит (каждый раунд)

- Добавь строку в таблицу «Раунды» файла `docs/audit/loop/state.md` (свежайший раунд внизу):
  `| round | lens | head | candidates | confirmed | rejected | tracked | dry_streak | commit | note |`.
  `head` = короткий sha аудируемого HEAD; `dry_streak` = число раундов подряд с confirmed=0
  (включая текущий). В `commit` впиши `—` (sha неизвестен до коммита; коммит находится по сообщению).
- Новые находки — в `docs/audit/loop/findings.md` (формат в шапке файла). Отчёт раунда не нужен —
  реестр и есть отчёт; условие проявления пиши прямо в строке находки.
- **Коммит раунда трогает только пути `docs/audit/loop/**`**; каталог `docs/audit/` git-ignored,
  поэтому индексируй принудительно — `git add -f docs/audit/loop`. Сообщение:
  `audit(r<N>, <lens>): +<confirmed> confirmed, +<rejected> rejected — <кратко>`.

## Жёсткие правила (сводка)

Общий свод — `docs/loop/ROUND-COMMON.md`; здесь только то, что добавляет аудит.

- Одна линза за раунд. Ноль правок кода.
- «Продолжай, находок нет» — не вывод, а dry-остановка по правилу §4 и только по нему.
- Severity честные: не раздувай Low до High ради «улова», не глуши High до Low ради dry.

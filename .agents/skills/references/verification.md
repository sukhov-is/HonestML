# Адверсариальная верификация находок

Цель — отфильтровать галлюцинации и шум до того, как находка превратится в работу.
Производственные ревью-пайплайны (Anthropic security-review, CodeRabbit)
сходятся: отдельная верификация каждой находки отсеивает большинство ложных
срабатываний, и это дешевле, чем потерянное доверие к отчёту.

Протокол общий для двух потребителей: `project-audit` в фазе 3 верифицирует находки
фазы 1 (Critical/High/Medium по профилю), `implementation` — blocker/major своей
фазы Review.
Разделы про реестр и раунд скептиков относятся к аудиту; слепота, формулировка
задания, вердикты и циклы доработки действуют одинаково.

## Слепота — главное правило

Верификатор получает **только**:
- находку по схеме (заголовок, `file:line`, цитата-доказательство, сценарий);
- сами файлы (он читает реальный код, а не пересказ);
- релевантный контракт места: конвенцию из profile.md, строку ADR/дока,
  правило слоя — то, против чего находка заявлена.

Верификатор **никогда** не получает: рассуждения автора находки, его
оценку уверенности, твоё мнение, количество других находок. Любая из этих утечек
превращает проверку в подтверждение чужого вывода.

Формулировка задания — всегда «найди, что в этой находке неверно», никогда
«проверь, корректна ли». Верификатор read-only: только чтение кода, без
shell-команд с записью и без правок.

## Вердикты

Принудительный вердикт по каждой находке — уклончивое «возможно» не
принимается:

| Вердикт | Значение | Действие |
|---|---|---|
| `CONFIRMED` | проблема реальна, сценарий воспроизводим по коду | в отчёт |
| `TRADE-OFF` | код намеренный, осознанный компромисс (видно по докам/истории) | в отчёт как Info с пометкой, кандидат в learnings.md |
| `REJECTED(misread)` | находка неверно прочитала контракт/код | в таблицу отклонённых с причиной |
| `REJECTED(noise)` | формально верно, но последствий нет | в таблицу отклонённых с причиной |

К вердикту обязательно обоснование с цитатой кода. Вердикт может **понизить
severity** (сценарий реален, но масштаб меньше заявленного) — это нормальный
исход, фиксируй старое и новое значение.

**Отклонение с причиной — успех верификатора, не неудача.** Без этой установки
верификатор стремится всё подтвердить.

## Реестр — три таблицы (`02-ledger.md`)

```
## Подтверждено   | id | sev/conf | заголовок | file:line | вердикт+цитата |
## Спорно         | id | позиции сторон рядом, без принудительного разрешения |
## Отклонено      | id | заголовок | причина отклонения |
```

Отклонённые — полноценная часть выхода: таблица предотвращает повторный флаг
на следующем аудите и показывает пользователю, что фильтр работал. Если
подтверждено ≈100% находок подряд — верификация сломана (подтверждающий
театр): перечитай этот файл, проверь слепоту чартеров, перезапусти партию.

## Циклы доработки

Находка без доказательства/сценария до верификатора не доходит — верни автору
направления (продолжи того же агента через `followup_task`: контекст находки у
него, новый спавн дороже и слабее). После `REJECTED` автор может один раз
донести доказательство → повторная верификация. Кэп: 2 цикла на находку,
дальше — в отклонённые или в спорные.

## Спорные находки — раунд скептиков (глубокий профиль)

Для каждой спорной — один свежий скептик с заданием опровергнуть позицию,
которая сейчас выигрывает (а не подтвердить). Выживает — переносится в
подтверждённые с пометкой «после раунда скептиков»; нет — рядом обе позиции,
решает пользователь. Один раунд, не больше: дальше отдача убывает.

## Что verification НЕ делает

- Не переоценивает направления целиком — только конкретные находки.
- Не ищет новые проблемы — это работа фазы 1 (нашёл попутно — верни
  оркестратору отдельной строкой, не вшивай в вердикт).
- Не правит код и не предлагает дизайн — только вердикт по заявленному.

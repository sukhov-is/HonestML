# Implementation Orchestrator

## Режимы

**Design-backed** идёт по пакету `docs/architecture/<feature>/` с `design-gate = go`:
границы и матрица уже заданы architecture-design. **Direct** идёт по Accepted Spec
либо явно принятым критериям поведения в известной области кода, когда изменение
помещается в существующие модули, порты, адаптеры и контракты. Числового потолка по
файлам или проверкам у direct нет: режим выбирается по характеру границы и контракта,
а не по размеру diff. Новая граница, публичный API или контракт порта, миграция
формата `ModelArtifact` или существенный компромисс по честности оценки/NFR — не
direct: передай задачу в architecture-design.

Зафиксируй выбранный режим и авторитетный источник поведения. Различия режимов —
таблица в `references/implementation.md`; дальше пайплайн общий.

## Пайплайн

### 0. Gate-check — убедись, что дизайн готов

- **Design-backed:** прочитай `06-traceability.md`. Требуются design-gate =
  **go**, заполненные планом строки матрицы и статус `planned`. No-go или
  неполная трассировка возвращают задачу в architecture-design.
- **Direct:** проверь, что поведение и критерии приняты, а изменение проходит
  границу direct mode. Неясность продукта возвращается в spec-driven-development,
  архитектурное решение — в architecture-design.

### 1. Plan
2–5 milestone-шагов, **каждый с verify-критерием**
(`шаг → verify: [команда/тест/метрика]`). Следуй `<plan_usage>` из правил проекта.
Заведи план через `update_plan`; в design-backed mode сохрани копию в `08-plan.md`.

### 2. Tests → Implementation — код в `src/`, тесты в `tests/`
Строй по `references/implementation.md` (**читай перед началом**):
- **Порядок сборки изнутри наружу**: entities → порты → use-cases → адаптеры →
  composition root. Внутренние слои пишутся и тестируются первыми, без инфраструктуры.
- **Цикл TDD на каждое требование/критерий**: `red → green → refactor → trace` —
  тест из критерия приёмки, минимальный код до зелёного, затем evidence в
  трассировку режима.
- **Definition of Done на milestone**: тесты зелёные (вкл. числовые NFR), lint
  чист, слои соблюдены, evidence требований закрыто, нет дрейфа от принятого
  контракта, минимальный диф.
- **Батчинг ходов**: независимые вызовы (аргументы не зависят от результатов
  соседей) — одним сообщением; проверки ruff, узкого mypy и lint-imports — отдельными
  `shell_command`. Последовательными остаются только зависимые цепочки
  (red → green → refactor). Каждый лишний ход заново оплачивает весь накопленный контекст.
Соблюдай слои и границы своего режима — направление зависимостей строго внутрь
(`../architecture-design/references/architecture-handbook.md`).

**Живая спека:** реализация обязана соответствовать текущей принятой ревизии
spec — держи её открытой, если она и есть источник поведения. Если реализация
меняет пользовательский результат, scope,
safety-границу или критерий успеха — до completeness-gate пройди lifecycle живой
спецификации из spec-driven-development (обновление в том же change-set →
`Draft` → повторное принятие), затем перепроверь затронутые требования, backlog
и дизайн. Технические детали, не меняющие продуктовый контракт, ревизии не
требуют.

### 2.5. Completeness-gate — до Review и полной suite
Переход к финальному Review разрешён, только когда одновременно выполнено всё:
- каждый milestone в TodoWrite имеет статус `completed` и свой verify прошёл;
- в design-backed mode каждая FR/NFR-строка `06-traceability.md` подтверждена
  фактом (ячейки «Реализация»/«Проверка» уточнены при расхождении с планом) и
  имеет статус `☑ done` (либо `accepted-risk` для принятого
  задокументированного риска);
- в direct mode каждый критерий принятой spec/контракта связан с фактическим
  кодом и зелёным тестом/метрикой, а реализованное поведение сверено с этим
  входным контрактом;
- в design-backed mode все заявленные модули, адаптеры, composition wiring,
  миграции и boundary-тесты существуют;
- точечные тесты затронутых областей зелёные.

В design-backed mode после фактического закрытия этих условий добавь в `08-plan.md` отдельной строкой с начала строки,
без markdown-обрамления и отступа: `Implementation milestones complete: yes`. Не добавляй её авансом:
Stop-hook читает маркер как сигнал завершения. Маркер синхронизирует состояние с драйвером, а не
доказывает результат — доказательство даёт `ops/loop/gates.ps1` (loop-contract → skill-parity →
instruction-parity → config-check → registers → check-index → ruff-format → ruff → lint-imports →
mypy → pre-commit → pytest).

Gate судит **полноту**: все строки закрыты и подтверждены фактом. **Правдивость** evidence проверяет
фаза 3 измерением «соответствие» — одну и ту же таблицу дважды не пересчитывай.

Незавершённый plan item, `planned` или `☐` — это команда продолжить реализацию, а не повод запускать полную
suite, Review или оформлять `NO-GO`. Полный `ops/loop/gates.ps1` запускай один раз после финального
ACCEPT; промежуточно используй только узкие проверки milestone.

### 3. Review
Проверь 4 измерения из `references/review.md`: **качество**, **безопасность**,
**оптимальность**, **соответствие** контракту. Первые три берут чек-лист и
FP-контракт из общей библиотеки линз `../references/lenses/` — передавай ревьюеру
файлы его линз. Схема делегирования — по таблице режимов. Находки — с вердиктом и ссылкой на нарушенное требование/ADR.
Blocker и major до постановки в очередь исправлений проходят слепую верификацию
(`../references/verification.md`): находка, которую не подтвердил непричастный проверяющий, — гипотеза.

Review findings образуют внутреннюю очередь исправлений этого же запуска: после
completeness-gate — ровно одна полная baseline-волна по схеме режима, слепая
верификация blocker/major, адресное закрытие каждой находки её автором, затем
ровно один свежий regression-reviewer по совокупной дельте исправлений. Новые
полные или свежие review-волны после него запрещены. Стабильные ID, durable state
и append-only реестры проходов и находок — по `references/review.md`; перед любым
делегированием прочитай это состояние, чтобы завершённый после resume проход не
запустился повторно.

Выход разрешён только после закрытия всех actionable ID и завершения protocol
markers:

`## Review state`
`## Review passes`
`## Review findings`
`Full review waves: 1`
`Fresh regression review waves: 1`
`Review protocol: complete`

Не откатывай собственную реализацию из-за review и не завершай работу статусом
`needs-fix`; внешний блокер оформляется только когда продолжение действительно
требует решения пользователя или изменения утверждённого дизайна.
Финальная сводка (место — по таблице режимов) содержит машинно-проверяемые строки
`Final verdict: ACCEPT` и `Open actionable findings: 0`. Верхнеуровневый verdict
обновляется текущим состоянием; append-only pass/finding registers сохраняются.

### 4. Final DoD и Changelog
После ACCEPT запусти полный `powershell -NoProfile -ExecutionPolicy Bypass -File ops/loop/gates.ps1 -Item <id пункта>`;
он идёт 28–40 минут, закладывай на вызов не меньше 45 минут (2700000 ms).
`-Item` оставляет вердикт гейта реестров в границах своего среза.
Такой вызов харнесс вернёт ячейкой: дожидайся её одним длинным `wait` с предельным
`yield_time_ms` (300000) и повторяй его, только пока ячейка жива — короткие опросы, циклы статуса и
sleep запрещены здесь ровно так же, как при ожидании ревьюеров. Красный gate возвращает в Fix того же
запуска; он не является терминальным статусом. После зелёного DoD переходи к changelog.

Если входом была spec, обнови evidence её критериев: отмечай выполненное только
по результатам инструментов этой сессии, а недоказанное оставляй открытым и
называй в handoff.

Допиши запись в `docs/implementation/changelog.md` в существующем формате
(`## [YYYY-MM-DD] Заголовок` → разделы `### Added` / `### Changed` / `### Tests`
и т.п., как уже в файле), кратко: что, где, ключевые ADR. Дата — из контекста
(`currentDate`), не выдумывай. Корневой `CHANGELOG.md` — пользовательский:
правь его, только когда изменение видно в публичном API.

## Делегирование субагентам

Фаза 3 (Review) — через `spawn_agent` с `fork_turns: "none"`; состав baseline —
по таблице режимов, результаты собирай через `wait_agent`. Что передать: источник
поведения (пакет `01-requirements/`, `04-adr/`, `05-design/`, `06-traceability.md`
либо Accepted Spec/явные критерии), список затронутых файлов кода и файлы линз его
измерения — без источника «соответствие» проверять не на чем. Зачем: ревью формирует
очередь исправлений и подтверждает ACCEPT перед финальным DoD, а его первичный
`NO-GO` запуск не завершает.

`Review collection mode: provider-native, non-polling`

Независимых ревьюеров запускай fan-out одним batch. Пока они работают, заверши доступную
локальную работу, затем ожидай через `wait_agent(timeout_ms: 1800000)`: 30 минут — только
потолок ожидания, любое сообщение или завершение будит вызов сразу. Обработай все пришедшие
результаты, зафиксируй состояние и, только если известны незавершённые ревьюеры, снова вызови
один длинный `wait_agent`. Повторные короткие `wait_agent`, циклы `list_agents`/status и
sleep запрещены. Если длинное ожидание истекло, один раз запроси у оставшихся ревьюеров
финальный вердикт либо описание блокера и снова перейди к длинному ожиданию; timeout не
останавливает ревьюера и не запускает его заново.

На длинных или рисковых прогонах (пороги — в таблице режимов) на закрытии каждого
milestone сделай acceptance-check свежим субагентом против критериев и diff milestone.
Это не Review-pass: он не создаёт finding IDs, не меняет `09-review.md` и не заменяет `B1`.

# Имплементация принятого контракта

Как строить код по архитектурному пакету либо по прямому контракту небольшой
фичи. Цель — чтобы реализация не разъехалась с принятым источником поведения:
каждый шаг проверяем, каждое изменение трассируется до требования.

## 0. Различия режимов

Всё, чем design-backed отличается от direct; дальше пайплайн общий.

| | Design-backed | Direct |
|---|---|---|
| Вход | пакет `docs/architecture/<feature>/`: `01-requirements/`, `04-adr/`, `05-design/`, `06-traceability.md` с `design-gate = go`, `07-design-review.md` | Accepted Spec либо явно принятые критерии и известная область кода |
| План | TodoWrite + копия в `08-plan.md` | только TodoWrite |
| Трассировка | матрица `06-traceability.md`: `planned` → `☑ done` | сверка критериев spec/контракта с кодом и тестами |
| Слои и границы | из `05-design/` | действующие границы проекта; менять их без дизайн-пакета нельзя |
| Review (фаза 3) | 4 линзы отдельными параллельными субагентами | один свежий ревьюер по всем 4 линзам; разделяй при высоком риске/размере |
| Промежуточные сверки milestone | при 3+ milestone | при 5+ milestone либо явно высоком риске |
| Маркер `Implementation milestones complete: yes` | в `08-plan.md` (машинный gate Stop-hook'а) | не создаётся |
| Сводка ревью (`Final verdict` / `Open actionable findings`) | `09-review.md` | итоговая сводка задачи |

## 1. Порядок сборки по слоям (build order)

Когда изменение проходит через несколько слоёв, строй **изнутри наружу** — от
самого стабильного к самому заменяемому. Локальный direct-инкремент остаётся в
существующей границе и не обязан искусственно затрагивать все слои. Внутренние
слои не знают о внешних, поэтому их можно написать и протестировать первыми, без
заглушек инфраструктуры.

```
1. Entities      — доменные модели и инварианты (чистые, без I/O)
2. Порты         — интерфейсы (Protocol/ABC), которые объявляют use-cases
3. Use Cases     — сценарии поверх entities и портов; тестируются на фейках портов
4. Адаптеры      — реализации портов поверх sklearn, бустингов, Optuna, I/O
5. Composition   — composition root: связывание зависимостей, конфиг, точка входа
```

Почему так: к моменту написания адаптера (шаг 4) контракт уже зафиксирован портом
(шаг 2) и проверен на use-case (шаг 3). Адаптер лишь «подключает» реальную деталь.
Если приходится писать use-case, упоминая конкретный адаптер, — порт пропущен,
вернись на шаг 2.

Для HonestML: `core/dataset.py` и `core/config.py` (1) → порт в `core/ports/`
(`CVSplitter`, `Estimator`, `Metric`) (2) → сценарий `application/oof_scorer.py`,
`application/feature_selection.py` (3) → `adapters/splitters.py`, `estimators.py`,
`boosting.py` как адаптеры (4) → `composition/build.py` и фасад (5).

**Контракты — часть дифа.** Слои охраняет import-linter (`.importlinter` в корне,
проверка `uv run lint-imports`). Контракты-allowlist'ы не видят новых модулей
сами: новый top-level пакет `honestml.<x>` добавь в `layers` контракта `layers`,
а пакет слоя use-case или адаптеров — ещё и в `modules` контракта
`usecases-independent-of-adapters`; модуль внутри существующего пакета контрактом
уже покрыт. Новая граница design-backed задачи берётся из
`05-design/dependency-graph.md`.
Иначе lint-imports останется зелёным, а инвариант тихо умрёт.

## 2. Пошаговый цикл TDD (на каждое требование)

Реализуй по одному требованию за раз. Тест пишется из **критерия приёмки**
требования — так тест и требование совпадают по смыслу, а не живут отдельно.

```
red    → напиши падающий тест по критерию FR-N/NFR-N либо direct-контракта
green  → минимальный код, чтобы тест прошёл (не больше, чем нужно)
refactor → почисти, не меняя поведение; тесты остаются зелёными
trace  → закрой строку матрицы (`☑ done`) либо дополни direct-сверку
```

Принципы:
- **Один критерий приёмки → минимум один тест.** NFR с числовым порогом
  проверяется тестом производительности/бенчмарком или метрикой, не «на глаз».
- Бизнес-правила (entities/use-cases) тестируются **без I/O** — порты подменяются
  фейками/стабами. Это быстрые, детерминированные тесты ядра.
- Адаптеры тестируются отдельно, узким набором, на реальной библиотеке за портом
  (`tests/integration/`), а не на фейке.
- **NFR честности оценки проверяются явными тестами:** нет утечки таргета —
  таргет-энкодинг, отбор признаков и калибровка видят только train-часть фолда;
  нет утечки через время — purge и embargo вычищают окрестность границы;
  детерминизм — два прогона с одним сидом дают тот же лидерборд и тот же
  артефакт. В design-backed mode они закрывают NFR честности из
  `01-requirements/`; в direct — соответствующий критерий spec/контракта.
- Не пиши код вперёд теста и вперёд требования — иначе появляется код без
  трассировки (scope creep, запрещён правилами проекта).
- `uv run pytest <путь> -q 2>&1 | tail -20` после каждого green; гоняй узко по
  затронутому модулю (никогда `-v` на полной сюите — стотысячный выхлоп оплачивается
  каждым последующим ходом). Полный прогон — один раз после completeness-gate и финального Review ACCEPT одним
  foreground-вызовом `powershell -NoProfile -ExecutionPolicy Bypass -File ops/loop/gates.ps1 -Item <id пункта>`
  (28–40 минут, без фоновых прогонов и поллинга).
- Независимые чтения запускай параллельно доступными read-only вызовами; поиск файлов
  и текста выполняй через `rg --files` и `rg`. Промежуточные проверки запускай
  отдельными `shell_command`: `uv run ruff check src tests`, `uv run mypy src` и
  `uv run lint-imports`.
  Каждый отдельный ход заново оплачивает весь накопленный контекст.

Конкретные шаблоны pytest, инварианты пайплайна (нет утечки таргета, детерминизм
по сиду, round-trip артефакта) и тесты честной оценки — `../../references/testing-patterns.md`.

## 3. Definition of Done (на каждый milestone плана)

Milestone из `08-plan.md` (design-backed) или `update_plan` (direct) считается
завершённым, только когда выполнены **все** применимые пункты — иначе он остаётся
`in_progress`:

- [ ] Тесты по критериям приёмки соответствующих FR/NFR — **зелёные**
      (`uv run pytest`), включая числовые NFR.
- [ ] Lint/типизация — **чисто**: `uv run ruff format --check src tests`,
      `uv run ruff check src tests` и `uv run mypy src` без ошибок. В отчёте
      приведи строку вывода `no issues found in N source files` как
      доказательство охвата.
- [ ] Слои — **детерминированно**: `uv run lint-imports` зелёный, и новые
      модули/границы покрыты контрактами (см. «Контракты — часть дифа» выше).
      Прозой проверяй только то, что контрактом не выражается: DTO через
      границу, Humble Object, порт vs конкретный адаптер внутри одного пакета.
- [ ] В design-backed mode соответствующие строки `06-traceability.md` закрыты:
      ячейки «Реализация»/«Проверка» уточнены при расхождении с планом,
      статус → `☑ done`. В direct mode каждый критерий spec/контракта связан
      с кодом и зелёной проверкой в итоговой сверке.
- [ ] Реализация не отклонилась от принятого контракта; для design-backed это
      включает ADR, для direct — Accepted Spec/явные критерии и существующие
      архитектурные границы.
- [ ] Нет кода без требования и нет нереализованных требований в рамках milestone.
- [ ] Минимальный диф: удалены только орфаны (импорты/переменные/функции),
      которые осиротели из-за этого изменения.

Каждый пункт DoD закрывай только по фактическому выводу инструмента из этой
сессии (pytest, ruff, mypy, lint-imports) — не по памяти; упавшее и пропущенное называй
явно, с выводом команды. Честный красный статус лучше ложного зелёного.

Переход к фазе Review открывает completeness-gate скила (SKILL.md, фаза 2.5); там же
объявлен маркер, который пишется в `08-plan.md` в design-backed mode. Незакрытый
milestone или строка `☐` — команда продолжать этот же запуск, а не повод для полного
прогона гейтов. Review finding возвращает в TDD-цикл этого запуска; не откатывай WIP и
не передавай исправление следующему раунду.

## 4. Связь с остальным пайплайном

- **Вход design-backed:** `08-plan.md`, `04-adr/`, `05-design/`, матрица.
- **Вход direct:** Accepted Spec/явные критерии и TodoWrite-план с verify.
- **Выход:** код в `src/`, тесты в `tests/`, фактическое evidence выбранного
  контракта, готовность к Review и Changelog.

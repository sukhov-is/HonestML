# Ревью реализации — четыре измерения

Ревью проверяет реализацию по четырём измерениям: **качество**, **безопасность**,
**оптимальность** и **соответствие** принятому контракту. Схему запуска (отдельные
параллельные субагенты либо один свежий ревьюер) задаёт таблица режимов в SKILL.md.
Каждая находка ссылается на нарушенное требование, ADR или правило слоя и несёт
вердикт серьёзности.

Субагент не видит контекст сессии. Для design-backed передай пути к
`01-requirements/`, `04-adr/`, `05-design/`, `06-traceability.md`; для direct —
Accepted Spec/явные критерии. Всегда передавай точный список затронутых файлов
кода. Без источника поведения измерение «соответствие» сверять не с чем.

**Скоуп чтения фиксируй в промпте субагента**: измерение работает только по переданному
списку файлов и переданному контракту (пакет дизайна либо direct-вход); обход
соседних модулей — только при конкретном подозрении,
с названной причиной. Каждое лишнее чтение ревьюер оплачивает всем своим контекстом.

Формат находки:
`[измерение] серьёзность(blocker/major/minor) — суть — файл:строка — нарушает FR/NFR/ADR-N — рекомендация`

## Откуда берутся чек-листы

Первые три измерения работают по общей библиотеке линз `../../references/lenses/` —
той же, которой аудирует кодовую базу скил project-audit:

| Измерение | Линзы | Дополнительно |
|---|---|---|
| Качество | `correctness.md`, `cleanliness.md`, `architecture.md` | правила слоёв — `../../architecture-design/references/architecture-handbook.md` |
| Безопасность | `security.md` | предметный чек-лист проекта — `../../references/security-checklist.md` |
| Оптимальность | `performance.md` | числовые NFR принятого контракта |

Передавай ревьюеру файлы его линз, а не пересказ. Линзы описывают аудит проекта; в
ревью реализации отличаются две вещи: **скоуп** — изменённые файлы и их прямые соседи
вместо всей кодовой базы, и **шкала** — blocker/major/minor вместо severity и
уверенности аудита. Остальное действует как есть, и именно оно держит точность: раздел «не
твоё» разводит измерения между собой, жёсткие исключения FP-контракта отсекают шум,
а требование доказательства запрещает находку без цитаты кода и сценария поломки.

## Соответствие контракту

Четвёртое измерение собственное: сверка с выбранным источником поведения, замыкающая
цепочку `требование → код → evidence`.

- Evidence правдиво: тест из ячейки «Проверка» существует и проверяет заявленное
  поведение, а не соседнее; ссылка на реализацию ведёт к коду, который требование
  закрывает. Полноту заполнения матрицы подтвердил completeness-gate — здесь судится
  честность записей, а не их наличие.
- Принятые ADR отражены в коде, когда они есть; нет дрейфа от источника поведения.
- Нет нереализованных требований и нет кода без требования (scope creep).
- Реализация уважает выбранные слои и порты из фазы Design.
- Документация и changelog обновлены; ADR не переписаны задним числом.

## Верификация blocker/major

Находка — недоверенное утверждение, пока её не проверил тот, кто не участвовал в её
формулировании. Для blocker и major применяй протокол
`../../references/verification.md`: слепой верификатор получает только саму находку
(заголовок, файл:строка, цитата, сценарий) и контракт места — ни рассуждений автора,
ни твоего мнения, ни числа других находок. Задание всегда «найди, что здесь неверно»,
а не «проверь, корректна ли»; вердикт принудительный, и отклонение с причиной — успех
проверки, а не её неудача. Minor не верифицируются: цена ошибки там ниже цены проверки.

Закрытие находки подтверждает её автор — продолжи того же агента через `followup_task`,
у него уже есть контекст. Передай stable ID, исходный сценарий, нарушенный контракт
и исправленный diff. Closure-проверка отвечает только на два вопроса: устранён ли
исходный сценарий и не нарушены ли прямо затронутые инварианты. Она не расширяет
скоуп и не превращается в новый аудит. После resume без доступного автора один
replacement-reviewer получает тот же closure-пакет и те же ограничения.

## Сбор fan-out

Запусти независимых ревьюеров вместе, используй свободное время для локальной работы,
затем вызови один длинный `wait_agent(timeout_ms: 1800000)`. Это потолок, а не задержка:
вызов возвращает управление при первом фактическом сообщении или завершении. Обработай
пришедшие результаты и повтори длинное ожидание только для известных незавершённых
ревьюеров. Не опрашивай их короткими `wait_agent`, `list_agents`, status-циклами или sleep.
Истечение потолка не отменяет работу: один адресный запрос результата или блокера, затем
снова длинное событийное ожидание.

## Durable state и идентичность находок

В design-backed mode создай `09-review.md` в начале baseline, а не после ACCEPT.
Он хранит состояние Review между продолжениями процесса и новыми запусками.
Перед любым делегированием прочитай его и продолжи незавершённую стадию;
завершённую стадию не повторяй. Direct mode следует тем же pass/ID-правилам
в структурированной сводке текущей задачи, но не создаёт архитектурный пакет.

Секция `## Review state` содержит:

```text
Current stage: baseline|closure|regression|complete
Baseline pass: pending|running|complete
Baseline closure: pending|running|complete|not-required
Regression pass: pending|running|complete
Regression closure: pending|running|complete|not-required
Current artifact fingerprint: <HEAD>:<git-diff-hash>
Open actionable IDs: <comma-separated IDs or 0>
```

Fingerprint считай для текущего артефакта командой
`git diff --binary HEAD | git hash-object --stdin` и записывай вместе с `HEAD`.
Если процесс прервался на `running`, продолжи тот же pass ID: используй живых
агентов, а недоступных замени только в их прежнем скоупе.

Секция `## Review passes` содержит append-only реестр:

```text
| pass | kind | artifact fingerprint | scope | reviewer | finding IDs | status |
| B1 | baseline | ... | four dimensions/current changed files | ... | ... | complete |
| C1 | closure | ... | listed IDs + fix diff | original authors | ... | complete |
| R1 | regression | ... | aggregate fix diff + affected invariants | fresh | ... | complete |
```

Допустимы ровно `B1` и `R1`; closure-записи продолжают адресную проверку
зарегистрированных IDs и не являются новой review-волной.

Секция `## Review findings` содержит append-only реестр:

```text
| ID | lens | severity | contract | location | failure scenario | author | status | closure evidence |
```

ID имеет формат `RV-B-NNN` для baseline или `RV-R-NNN` для regression, назначается
один раз и сохраняется при reopen, resume и повторной проверке. Линзу несёт колонка
`lens` той же строки — в идентификаторе она не дублируется. Дубликаты объединяются
под первым ID; status меняется между `open`, `rejected`, `fixed`, `closed`, но
строка не удаляется.

## Сводка ревью

В `09-review.md` для design-backed или в итоговой сводке direct mode:
1. Вердикт: можно ли принимать (`Open actionable findings: 0`).
2. Таблица находок по измерениям с серьёзностью и ссылками.
3. Незакрытые требования/evidence — отдельным списком.
4. Рекомендованные действия до принятия.

Каждое рекомендованное действие — очередь исправлений текущего implementation-запуска.
После baseline исходные авторы адресно подтверждают закрытие своих IDs. После
закрытия baseline-очереди один свежий reviewer выполняет `R1` только по совокупной
дельте исправлений и затронутым инвариантам. Новые подтверждённые находки `R1`
получают stable IDs и возвращаются тому же reviewer на closure; второй regression
или новый полный review не запускается. `NO-GO` — внутренний результат Review, а
не терминальный статус раунда; выход разрешён только после ACCEPT без открытых
**actionable**-находок — blocker, major и тех minor, для которых требуется правка.
Перед финальными строками добавь тремя отдельными строками без markdown-обрамления:
`Full review waves: 1`, `Fresh regression review waves: 1`,
`Review protocol: complete`.
Заверши сводку двумя отдельными строками без markdown-обрамления: `Final verdict: ACCEPT` и
`Open actionable findings: 0`. Они фиксируют итог последней проверки, а не историю промежуточных
итераций.

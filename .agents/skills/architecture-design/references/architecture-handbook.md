# Architecture Handbook — Clean Architecture

Общие правила проектирования на базе Clean Architecture (Robert C. Martin).
Цель — структура, в которой бизнес-логика не зависит от деталей (ML-библиотеки,
фреймы данных, формат хранения), а изменения деталей не ломают ядро.

## Содержание
1. Слои и правило зависимостей
2. Границы и пересечение границ
3. Порты и адаптеры
4. SOLID на уровне компонентов

6. Запахи и красные флаги

## 1. Слои и правило зависимостей

Концентрические слои, зависимости направлены **только внутрь**:

```
[ Frameworks & Drivers ]   ← sklearn, CatBoost/LightGBM/XGBoost, Optuna, ONNX, polars, файлы
   [ Interface Adapters ]  ← Reader, сплиттеры, обёртки моделей, сериализаторы, кэш, трекер
      [ Use Cases ]        ← сценарии приложения (orchestration бизнес-логики)
         [ Entities ]      ← доменные модели и правила, не зависящие ни от чего
```

**Правило зависимостей (главное):** исходный код внутреннего слоя не знает
ничего о внешнем. Имена из внешних слоёв (классы, функции, переменные) не
упоминаются во внутренних. Поток управления может идти наружу — но зависимость
исходного кода всегда внутрь, через инверсию (DIP).

- **Entities** — доменные правила и модели. Самые стабильные.
  Не импортируют ничего из инфраструктуры.
- **Use Cases** — прикладные сценарии: «прогнать срез: обучить кандидатов по
  фолдам и собрать лидерборд». Оркеструют entities, зависят от **портов**
  (интерфейсов) вместо конкретного внешнего мира.
- **Interface Adapters** — преобразуют данные между use-case и внешним миром:
  чтение входа, нарезка фолдов, обёртки моделей, сериализация. Реализуют порты.
- **Frameworks & Drivers** — ML-библиотеки, фреймы данных, движок HPO, ONNX
  runtime. Максимально заменяемы. Сюда же — composition root, где всё связывается.

## 2. Границы и пересечение границ

- Граница проходит там, где **разная скорость/причина изменений** (обёртка над
  библиотекой меняется иначе, чем правила честной оценки) — это ось разделения
  по SRP на уровне модулей.
- Через границу передавай **простые структуры данных** (numpy-массивы, dataclass,
  pydantic-модели), не внутренности адаптера. Не протаскивай фрейм конкретной
  библиотеки или объект сторонней модели в use-case.
- Зависимость через границу всегда указывает на более стабильную сторону.
- **Humble Object**: труднотестируемое (I/O, тяжёлая библиотека) выноси в тонкий
  слой без логики; логику держи в тестируемом объекте по другую сторону границы.

## 3. Порты и адаптеры (инверсия зависимостей)

Use-case не вызывает библиотеку напрямую — он зависит от **порта** (абстрактного
интерфейса), объявленного во внутреннем слое. Адаптер во внешнем слое
**реализует** порт. Так стрелка зависимости разворачивается внутрь.

```python
# внутренний слой: порт (что нужно сценарию)
class CVSplitter(Protocol):
    def split(self, dataset: Dataset) -> Iterator[Fold]: ...

# адаптер во внешнем слое: реализация порта поверх конкретной схемы нарезки
class TimeSeriesSplitter:
    def split(self, dataset: Dataset) -> Iterator[Fold]:
        ...  # знает про ось времени и purge/embargo; порт про них не знает
```

Use-case импортирует `CVSplitter`, но никогда — `TimeSeriesSplitter`.
Связывание происходит в composition root.

## 4. SOLID на уровне компонентов

- **SRP** — у модуля одна причина для изменения (один «актор»/заинтересованная
  сторона). Если файл меняют по двум разным причинам — раздели.
- **OCP** — расширяй через новые реализации портов, а не правкой ядра.
- **LSP** — реализации порта взаимозаменяемы без сюрпризов в контракте.
- **ISP** — узкие порты под конкретный сценарий вместо «толстых» интерфейсов;
  опциональная способность — отдельная role-интерфейс, а не ветка по `hasattr`.
- **DIP** — зависим от абстракций (портов), детали зависят от абстракций.

Принципы связности компонентов: REP/CCP/CRP (что класть в один компонент) и
ADP/SDP/SAP (граф зависимостей — ацикличный, в сторону стабильности и
абстрактности). Циклов в графе модулей быть не должно.

## 5. Применение к стеку HonestML

Проекту (Python, один процесс, всё в памяти, ввод через `Reader`) слои ложатся так:

| Слой | Что здесь у HonestML |
|------|----------------------|
| Entities | `honestml.core`: `Dataset`, `Fold`, `FeatureSchema`, `RunConfig`, `Task` и порты в `core/ports/` |
| Use Cases | `honestml.application`: `run_slice`, OOF-скоринг, отбор признаков, HPO, ансамблирование, отчёт прогона |
| Interface Adapters | `honestml.adapters`: `reader.py`, `splitters.py`, `estimators.py`, `boosting.py`, `serializers.py`, `candidate_cache.py`, `tracking.py` |
| Frameworks & Drivers | sklearn, CatBoost/LightGBM/XGBoost, Optuna, MLflow, ONNX, polars/pandas; сборка — `honestml.composition` |

Практика:
- Порядок слоёв задаёт контракт `layers` в `.importlinter`:
  `composition → application → adapters → core`; `honestml.application` и
  `honestml.adapters` при этом взаимно независимы — импорт между ними запрещён в
  обе стороны контрактом `usecases-independent-of-adapters`.
- `honestml.core` не импортирует ни ML-библиотеки, ни polars/pandas — это
  контракт `core-independence` в `.importlinter`, а не договорённость.
- Адаптеры реализуют порты `honestml.core.ports`; use-case видит порт, а не класс
  адаптера — контракт `usecases-independent-of-adapters`.
- Разрешение конфига и сборка зависимостей — в `honestml.composition`
  (`build.py`, `facade.py`), не в бизнес-логике.
- Пути с I/O и тяжёлыми библиотеками тонкие (Humble Object), а правила честной
  оценки — чистые и синхронно тестируемые.

## 6. Запахи и красные флаги

- `honestml.core` импортирует polars/sklearn/бустинг — нарушено правило
  зависимостей (`core-independence` красный).
- Use-case упоминает конкретный класс адаптера — нет инверсии (нужен порт).
- Цикл в графе зависимостей модулей — нарушен ADP.
- Логика честной оценки внутри обёртки библиотеки или внутри фасада — нет
  Humble Object.
- Фрейм конкретной библиотеки или объект сторонней модели протекает в
  use-case/entities — граница пересечена «грязно».
- Один модуль меняют по нескольким несвязанным причинам — нарушен SRP.

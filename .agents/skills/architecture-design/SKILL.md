# Architecture Design Orchestrator

Скил ведёт архитектурную задачу до **утверждённого, проверяемого дизайна**,
готового к реализации, на базе **Clean Architecture (Robert C. Martin)**. Главная
ценность — не отдельные артефакты, а **сквозная трассировка**: каждое требование
доходит до проверки, и любое решение можно объяснить требованием, которое его
породило. Финиш — design-gate; код по этому дизайну пишет отдельный скил
`implementation` (фазы Plan → Tests → Implementation → Review → Changelog).

## Вход и граница задачи

Перед созданием пакета зафиксируй:

1. источник задачи и ожидаемый результат;
2. известные границы, ограничения и критерии успеха;
3. as-is контекст, который затронет дизайн.

Вход считается достаточным, когда можно отличить архитектурное решение от
непринятого продуктового выбора. Accepted Spec, backlog slice и состав
требований эпика-носителя в `docs/loop/backlog.md` полезны, но не обязательны
одновременно. Для архитектурного фикса достаточно подтверждённой причины
дефекта, ожидаемого поведения и границы изменения.
Недостающие детали архитектурного контракта уточняются в Research и оформляются
локальными FR/NFR. Если неизвестно само желаемое поведение, верни вопрос в
spec-driven-development; если не установлена причина сбоя — в
debugging-and-error-recovery.

## Когда что запускать

Пакет проходит все фазы; глубину выбирает не пропуск фаз, а **контур ревью**
(фаза 8) и опциональность отдельных артефактов. Любой пакет **финиширует на
design-gate** — код не пишется здесь (это скил `implementation`).

**Brownfield (изменение существующей системы — типичный случай HonestML):**
сначала зафиксируй **as-is** на фазе Research (текущая структура, неявные
действующие решения — при необходимости оформи их baseline-ADR со статусом
`Accepted`), затем веди FR/NFR и трассировку **по дельте**
(что меняется), а не по всей системе с нуля.

Заведи план через `update_plan` с фазами как milestone-пунктами.

### Опциональность артефактов

| Фаза / артефакт | Когда нужен |
|---|---|
| 00-research | всегда (для brownfield — фиксирует as-is) |
| 01-requirements (локальные FR/NFR + ссылки на источники) | всегда |
| 02-drivers + риски | всегда |
| 03-spikes | только рисковые неизвестные (иначе пропуск) |
| 04-adr | на каждое значимое решение |
| 05-design/design | небольшой пакет: компонентный вид и граф зависимостей одним файлом вместо отдельных c4/dfd/dependency-graph |
| 05-design/c4 (Context+Container) | почти всегда; Component — по необходимости |
| 05-design/dfd | только для пайплайнов данных (трансформации признаков, нарезка фолдов, путь инференса) |
| 05-design/dependency-graph | всегда при Clean Architecture (доказывает правило слоёв) — отдельным файлом или разделом `design.md` |
| 05-design/operational | всегда, где меняется сериализуемый контракт, конфиг или поведение прогона (Day-2) |
| 06-traceability | всегда (ядро) |
| 07-design-review | независимое ревью перед gate: лёгкий контур — пара «структурная + адверсариальная корректность домена» + верификатор закрытия; полный — 2 стадии fan-out + верификатор (фаза 8) |
| 08-plan, реализация, ревью кода, changelog | не здесь — это скил `implementation` |

## Артефакты и куда они пишутся

Всё на **русском языке**, в `docs/architecture/<feature-slug>/`:

```
docs/architecture/<feature>/
├── 00-research.md              # фаза 1
├── 01-requirements/
│   ├── FR.md                   # функциональный контракт задачи
│   └── NFR.md                  # качественный контракт задачи
├── 02-drivers.md               # драйверы + риск-реестр
├── 03-spikes/                  # (опц.) результаты POC по рисковым решениям
│   └── SPIKE-NNNN-<slug>.md
├── 04-adr/ADR-NNNN-<slug>.md   # по одному решению на файл
├── 05-design/
│   ├── design.md               # компонентный вид и граф зависимостей одним файлом (малый пакет)
│   ├── c4.md                   # Context/Container/Component (Mermaid)
│   ├── dfd.md                  # потоки данных
│   ├── dependency-graph.md     # слои + направление зависимостей
│   └── operational.md          # Day-2: контракты, релиз, воспроизводимость, бюджеты
├── 06-traceability.md          # ★ матрица трассировки + вердикт design-gate (ядро)
└── 07-design-review.md         # независимое ревью дизайна (фаза 8)

# плоский реестр решений уровня продукта, куда публикуется принятое решение:
# docs/adr/ADR-NNNN-<slug>.md

# создаются скилом implementation в той же папке:
# 08-plan.md (план реализации), 09-review.md (ревью кода),
# docs/implementation/changelog.md (финальная запись)
```

Шаблоны лежат в `assets/` — копируй их, не выдумывай структуру заново. Каркас пакета
разворачивай **одним `shell_command`** (создание каталогов + копирование шаблонов),
а не серией отдельных операций.
Независимые чтения и правки разных файлов батчь в одном сообщении (аргументы не зависят
от результатов соседей) — каждый лишний ход заново оплачивает весь накопленный контекст.
Существующие файлы правь точечным `apply_patch`; полная замена — только для маленьких
или свежесозданных.

## Пайплайн

### 1. Research — `00-research.md`
Перед делегированием перегенерируй индекс решений
(`uv run python ops/loop/index_decisions.py --write`) и найди по нему смежные пакеты: одна строка на
решение с его пакетом, статусом и заголовком снимает коллизию номеров — `ADR-0087` существует в
двух пакетах и означает две разные вещи. **Найденные пути передавай внутри самого задания
субагенту**, а не отсылкой «загляни в индекс»: субагент стартует без твоего контекста, и
несозданная им ссылка для него не существует.
Делегируй **субагенту** через `spawn_agent` с `fork_turns: "none"` и явно
ограниченной read-only задачей, когда обзор широкий: изучить существующий код, домен,
ограничения, аналоги. Узкую сверку по уже известным путям делай сам — чтение в основной
сессии попадает в кэш, а субагент оплачивает свой контекст с нуля. Субагент возвращает:
контекст, существующие абстракции для переиспользования, ограничения, открытые вопросы.
Для внешних библиотек используй доступную официальную документацию или MCP, для
незнакомых концепций — web.
**Инфраструктурная задача** — сериализация и хранение артефактов, движок HPO,
трекинг экспериментов, экспорт модели, кэш прогона, параллелизм, всё, где класс
решения давно устоялся: субагент возвращает и внешние решения этого класса,
пригодные для нашего стека, с датой последнего релиза и статусом поддержки;
живость устанавливается фактом, а не памятью модели. Они идут в «Рассмотренные
варианты» ADR наравне с собственной реализацией: Research отвечает за полноту
списка, выбор делает фаза 5 по драйверам.
**Brownfield:** зафиксируй здесь **as-is** — текущую структуру и действующие
неявные решения; значимые из них оформи baseline-ADR (статус `Accepted`), чтобы
дельта трассировалась от реального состояния, а не от пустоты.
В шапке зафиксируй доступные источники задачи: spec, FR/NFR, backlog, ADR или
описание подтверждённого дефекта. Research уточняет границу изменения и может
вскрыть пропущенные требования.
**Открытые вопросы не теряй:** каждый переноси либо в риск-реестр (фаза 3) с
реакцией, либо в кандидаты на spike (фаза 4); ни один не должен дожить до ADR
неразрешённым.

### 2. Requirements — `01-requirements/FR.md`, `NFR.md`
Собери полный локальный контракт архитектурной задачи
(`assets/FR.template.md`, `assets/NFR.template.md`):

- **FR** описывают наблюдаемое поведение и сценарии; ID — `FR-1`, `FR-2`, …;
- **NFR** задают проверяемые свойства и условия; ID — `NFR-1`, `NFR-2`, …;
- каждое требование атомарно, имеет критерий приёмки и источник;
- при наличии Accepted Spec, backlog-среза или состава требований эпика-носителя
  в `docs/loop/backlog.md` сохрани ссылки на них, а локальный контракт
  сформулируй в масштабе текущей задачи;
- пробелы, без которых дизайн будет неполным, добавляй как
  `design-discovered`; продуктовые решения, меняющие согласованный scope или
  пользовательское поведение, отрази в исходной spec, верни её в `Draft` и
  повторно согласуй до design-gate;
- существенные находки вне текущей границы оформи кандидатами будущих срезов —
  одной строкой каждый в список «Кандидаты (не выбираются)» эпика-носителя в
  `docs/loop/backlog.md`: `` `id` — суть; источник: ревью `среза`; закрывает: FR/NFR-клауза | — ``,
  не больше трёх на пакет. Кандидат регистрирует находку и не является заданием:
  срезом его делает владелец, requirements-planning с квитанцией или раунд петли
  по правилу её контракта при открытой строке требования. Находка, которой нет
  в составе требований эпика, идёт в requirements-planning — состав требований
  эпика в этом скиле не правится.

### 3. Drivers + Риски — `02-drivers.md`
Из FR/NFR выведи **архитектурные драйверы** (`assets/drivers.template.md`) — то,
что реально формирует структуру: критичные NFR, ключевые сценарии, ограничения.
Драйвер — мост между «что нужно» и «как решили»; ссылается на FR/NFR.
В этом же файле — **риск-реестр**: для каждого значимого риска вероятность ×
влияние и реакция. Риск с высокой неопределённостью, влияющий на решение, —
кандидат на spike (фаза 4) *до* фиксации ADR.

### 4. Spike / POC — `03-spikes/SPIKE-NNNN-<slug>.md` (по необходимости)
Только для решений с высокой неопределённостью, где «на бумаге» не проверить
(производительность подхода, совместимость библиотеки, поведение под нагрузкой).
Узкий проверочный эксперимент (`assets/spike.template.md`): вопрос → что сделали →
измерения → вывод. Результат **питает ADR** фактами, а не догадками. Нет рисковых
неизвестных — пропусти фазу.

### 5. ADR — `04-adr/ADR-NNNN-<slug>.md`
На каждое значимое решение — отдельный ADR (`assets/ADR.template.md`):
контекст → рассмотренные варианты → решение → последствия. Номер — следующий
свободный в плоском реестре `docs/adr/`: принятое решение публикуется туда, копия
в пакете остаётся `Proposed`. Каждый ADR ссылается на драйвер(ы) и, если был, на
spike. Решения не переписывай задним числом — статусом `Superseded by ADR-XXXX`.
После добавления или правки ADR перегенерируй индекс —
`uv run python ops/loop/index_decisions.py --write`.

### 6. Design — `05-design/`
**Визуализирует принятые ADR**, а не изобретает заново. Строй на правилах
`references/architecture-handbook.md`; диаграммы Mermaid — `references/diagrams.md`:
- **C4**: Context → Container → Component (по необходимости).
- **DFD**: потоки данных между процессами/хранилищами.
- **Dependency graph**: слои Clean Architecture и **направление зависимостей
  строго внутрь** (к домену). Здесь ловятся нарушения. Финал артефакта —
  **дельта контрактов import-linter** (`.importlinter` в корне репозитория):
  каждая новая граница выражена контрактом либо явно помечена «контрактом не
  выражается» с причиной. Диаграмма визуализирует правило; доказывает его контракт.
- **operational.md** — Day-2 по `references/operational.md` (шаблон —
  `assets/operational.template.md`): эволюция сериализуемых контрактов
  (`ModelArtifact`, манифест прогона, ключ кэша), релиз и откат, детерминизм и
  бюджеты прогона, границы ошибок. Это проектные решения, а не пункты будущего
  ревью. Если фаза вскрыла новое решение — оформи ADR (вернись на 5).

### 7. Traceability — `06-traceability.md` ★
Собери матрицу (`assets/traceability.template.md`): `Источник → локальный FR/NFR
→ Драйвер → ADR → Реализация → Проверка`; **обновляй её на каждом шаге**, а не
одним заходом в конце. Прогони глазами весь локальный контракт — каждый элемент
должен доходить до способа проверки. Неполная строка = «дыра» в архитектуре.
Для слоевых/граничных NFR легитимная «Проверка» — контракт import-linter (его имя),
а не «ревью».
На этом этапе ячейки «Реализация»/«Проверка» содержат план, статус строки —
`planned`; implementation уточняет их фактом и переводит в `☑ done`.

### 8. Design Review — `07-design-review.md`
Независимая проверка **дизайна** (не кода) свежим взглядом — до gate, пока
переделка дёшева. Протокол целиком — `references/design-review.md`
(**читай перед фазой**): что получает ревьюер, определения линз, выбор между
лёгким и полным контуром, порядок закрытия находок и условие сходимости.
Лёгкий контур — дефолт; условие полного и всегда-полные случаи задаёт
`references/design-review.md`.

### 9. Design-gate — финальный чекпоинт (конец этого скила)
Контроль *до* реализации, чтобы ловить архитектурные дефекты, пока код не написан.
Критерии — чек-лист design-gate в `references/operational.md` (**читай перед фазой**);
других оснований для вердикта нет. Зафиксируй вердикт **go/no-go** в шапке
`06-traceability.md`. No-go → вернись к нужной фазе.

## Передача в реализацию — СТОП

Этот скил заканчивается на design-gate. **Код здесь не пишется.** На вердикте
`go`:
- **Остановись и отдай управление пользователю.** Выведи краткое резюме: что
  спроектировано, вердикт design-gate, путь к `docs/architecture/<feature>/`,
  и предложи следующий шаг — запустить скил `implementation`. **Не переходи к
  коду сам**, даже несмотря на `<solution_persistence>`: проектирование и
  реализация — разные воркфлоу, и решение «реализуем» принимает пользователь.
- Реализацию (Plan → Tests → Implementation → Review → Changelog) ведёт скил
  `implementation`, беря на вход этот пакет артефактов.

На вердикте `no-go` — вернись к нужной фазе, реализацию не предлагай.

## Делегирование субагентам

Фаза 8 (Design Review) идёт через `spawn_agent` с `fork_turns: "none"` всегда: её
ценность в независимом свежем контексте, который основная сессия дать не может. Фазу 1
делегируй по ширине обзора. Остальные фазы веди сам, опираясь на reference-файлы.

Что передать: Research-субагенту — пути к источникам задачи и коду плюс вопросы;
линзам ревью — то, что перечисляет `references/design-review.md`. Ревью читает
файлы и код, без web — вердикт опирается на пакет и реальный код.

Каркас разверни ДО спавна: перед research — `docs/architecture/<feature>/` из шаблонов
`assets/`.

## Reference-файлы

- `references/architecture-handbook.md` — правила Clean Architecture: слои,
  правило зависимостей, границы, порты/адаптеры, SOLID. **Читай перед фазами 6 и 8.**
- `references/diagrams.md` — Mermaid-синтаксис C4/DFD/графа зависимостей.
- `references/design-review.md` — протокол фазы 8: линзы, контуры, закрытие
  находок, сходимость. **Читай перед фазой 8.**
- `references/operational.md` — Day-2 (эволюция сериализуемых контрактов, релиз,
  воспроизводимость, бюджеты и границы ошибок) и чек-лист design-gate. **Читай перед фазами 6 и 9.**

Реализацию и ревью кода ведёт скил `implementation` (там и соответствующие
reference-файлы по сборке/TDD/ревью).

# Направление: Безопасность

## Чартер

Ищет уязвимости с **реальным путём воздействия** — те, что можно довести до
ущерба, а не теоретические. Поверхность узкая: сети и секретов в рантайме нет,
зато библиотека исполняет чужой код при загрузке артефакта и discovery плагинов
и пишет данные пользователя в артефакт, отчёт и логи. Не твоё: общая «гигиена»
без пути воздействия (→ чистота), необработанные ошибки без security-последствий
(→ корректность), секреты в TODO (→ твоё, если секрет настоящий).

Порядок работы: сначала пойми **собственные** защитные паттерны проекта
(валидация на границах, проверка целостности артефакта, экранирование в отчёте —
из карты и профиля), затем ищи отклонения от них и новые точки воздействия.
Трассируй поток данных от входа до чувствительной операции.

## Чек-лист

- Небезопасная десериализация: `joblib`/`pickle`-тело артефакта; порядок
  version-gate → проверка сумм → dispatch; файл, не покрытый `checksums`;
  `yaml.load`/`eval` где угодно.
- Path traversal: имя файла из манифеста, взятое не как basename; путь ко входным
  данным, склеенный из непроверенной строки; чтение за пределами каталога
  артефакта или каталога-источника.
- Исполнение стороннего кода: entry-point discovery плагинов, динамический импорт
  по строке из конфига, вызов чужой фабрики до валидации дескриптора.
- Валидация на границе: значения из манифеста и конфига, уходящие в sklearn и в
  файловые операции без проверки — манифест внешний вход.
- Раскрытие данных: сырые значения датасета в отчёте, логах и трекинге;
  HTML-рендер без экранирования того, что пришло из данных.
- Секреты: токены и ключи в коде, ноутбуках и git-истории.
- Зависимости: известные CVE из факта-среза фазы 0 (интерпретируй: достижима
  ли уязвимая поверхность из кода проекта).
- Критичные пути из profile.md (загрузка артефакта, плагин-контракт, чтение
  входных путей): для них инвертируй обычные исключения.

## FP-контракт

**Жёсткие исключения** (не флагать): теоретический DoS; «pickle небезопасен» как
таковое — граница доверия к артефакту объявлена, находка нужна там, где эта
граница нарушена; гонки в тестовом коде; устаревшие зависимости без достижимой
уязвимой поверхности; отсутствие audit-логов; «hardening»-пожелания без пути
воздействия; находки в markdown/доках.

**Прецеденты** (решены заранее): параметры публичного API, env-переменные и
данные, поданные самим пользователем, — доверенный вход; внутренние вызовы своих
модулей — доверенные (валидация на границах: Reader, загрузка артефакта, реестр
компонентов); конфиги, не попадающие в git, — не «секрет в коде».
**Захардкоженный боевой секрет** (ключ/токен/пароль вида `sk_live_…`, реальная
строка подключения) в коде под VCS — это экспозиция **независимо от того,
используется ли он сейчас**: VCS хранит историю, ключ всё равно надо ротировать.
Не понижай и не отклоняй такую находку по причине «нигде не вызывается».
Прецеденты конкретного проекта — из `docs/audit/profile.md`, если он заведён; они
старше этих.

## Доказательства

Критерий выдачи: «security-инженер уверенно поднял бы это в ревью». Для
Critical/High обязателен **сценарий воздействия** — конкретная цепочка
вход→путь→последствие (это и есть встроенная пред-верификация; не можешь
построить цепочку — понижай или отбрасывай). Экспресс и стандартный профили выдают
только **подтверждённое**; «вероятно» — с явной пометкой,
«гипотеза» — за их пределами.

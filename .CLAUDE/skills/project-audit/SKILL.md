# Project Audit Orchestrator

Скил ведёт аудит кодовой базы от инвентаризации до **проверенного** пакета
отчётов. Главная ценность — не сырой список замечаний, а **верифицированные
находки с доказательствами**: каждая привязана к `file:line` с цитатой кода,
имеет сценарий последствий и пережила слепую адверсариальную проверку.
Финиш — audit-gate: только отчёт и roadmap; фиксы — отдельное решение
пользователя.

## Принципы

- **Генерация ≠ верификация.** Находка аудитора — недоверенное утверждение,
  пока её не подтвердил отдельный верификатор со свежим контекстом. Слепая
  проверка (верификатор не видит рассуждений автора) — единственный надёжный
  фильтр галлюцинаций: иначе проверяющий подстраивается под чужой вывод.
- **Факты прежде суждений.** Сначала инструменты самого проекта (линтеры,
  тайпчекер, контракты импортов, сбор тестов, аудит зависимостей) дают
  ground truth; агенты интерпретируют измерения, а не заменяют их догадками.
- **Точность дороже полноты.** Ложные срабатывания разрушают доверие ко всему
  отчёту. Лучше пропустить теоретическую проблему, чем утопить реальную в шуме —
  отсюда FP-контракты, confidence-порог и обязательный сценарий последствий.
- **Сегмент вместо «весь проект каждому».** Аудитор, читающий проект целиком,
  тонет в контексте — отсюда размытые рассуждения и лишние ложные срабатывания.
  Дели проект на логические сегменты и давай аудитору ровно его регион; линзам,
  которым нужен весь проект, отведи отдельный сквозной проход по разу.
- **Документация проекта — спецификация аудита.** AGENTS.md, CLAUDE.md, ADR, доки
  архитектуры, конфиги линтеров — это и есть assert-набор, против которого
  проверяется код. Не выдумывай чужой проект — читай его собственные правила.
- **Аудиторы read-only.** Кто правит код, тот проверяет сам себя. Все агенты
  фаз 1–3 только читают; запись делает оркестратор и только в `docs/audit/`.

## Глубина

Выбери профиль по запросу и размеру задачи, озвучь одной строкой
(с ожидаемой длительностью) и заведи план (TodoWrite) с фазами:

| Профиль | Когда | Состав |
|---|---|---|
| **Экспресс** | один модуль/директория или 1–3 линзы по запросу | обычно один сегмент; региональные кластеры (+ нужные сквозные); без панели верификации — Critical/High проверяет сам оркестратор |
| **Стандартный** (дефолт) | весь проект, регулярный аудит | сегментация → региональные кластеры по сегментам + сквозные линзы; верификация Critical/High/Medium |
| **Глубокий** | перед релизом, «ничего не пропустить» | мельче сегменты + всё из стандартного + раунд скептиков по спорным + дубль-аудитор на 1–2 критичные сегменты/линзы |

Линзы можно сужать на любом профиле («аудит только безопасности и
производительности») — пропущенные явно перечисли в сводке как непокрытые.

## Артефакты

Всё на русском языке. Датированный пакет на каждый запуск + два живых файла:

```
docs/audit/
├── profile.md                  # живёт между аудитами: прецеденты проекта,
│                               #   критичные пути, конвенции, исключения
├── learnings.md                # живёт между аудитами: подавления отклонённых
│                               #   пользователем находок (паттерн + scope + причина)
└── <YYYY-MM-DD>/
    ├── 00-inventory.md         # карта проекта + факты инструментов (фаза 0)
    ├── 01-findings/                    # сырые отчёты: <сегмент>/<кластер>.md + сквозные (фаза 1)
    ├── 02-ledger.md            # реестр: подтверждено / спорно / отклонено (фазы 2–3)
    ├── 03-summary.md           # сводка: вердикты, матрица находок, что солидно
    └── 04-roadmap.md           # приоритизированный план улучшений (фаза 4)
```

## Пайплайн

### 0. Инвентаризация и факты — `00-inventory.md`

Дешёвая фаза, которая делает все остальные точными:

1. **Профиль проекта.** Если `docs/audit/profile.md` существует — загрузи.
   Иначе создай при первом аудите: определи стек по манифестам
   (`pyproject.toml`, `uv.lock`), собери конвенции (CLAUDE.md, AGENTS.md),
   карту документации (ADR, docs/), критичные пути (честность оценки, утечка
   таргета, десериализация артефактов, публичный API), исключения из универсума
   файлов (генерённое, lock-файлы, кэши, собранный сайт).
2. **Факты инструментов.** Запусти собственные гейты проекта: `uv run ruff check
   src tests`, `uv run mypy src`, `uv run lint-imports`, сбор тестов
   (`uv run pytest --collect-only -q`), состав зависимостей и extras в
   `pyproject.toml`, grep по TODO/FIXME/HACK и полям конфига. Выходы — факты
   для аудиторов, не находки: агент интерпретирует измерение, не повторяет его.
3. **Карта кодовой базы.** Делегируй read-only субагенту (`Agent`, тип
   `Explore`): модули, точки входа, слои, публичные контракты, размерности.
   Один агент строит карту, все аудиторы её переиспользуют — N агентов,
   заново исследующих репозиторий, жгут токены и расходятся в картине.
4. **Сегментация.** По карте раздели проект на **логические сегменты** —
   связные единицы (модуль, слой, подсистема, набор близких файлов), каждый
   достаточно мал, чтобы аудитор прочитал его вглубь. Размер и границы — твоё
   суждение: мелкий проект = один сегмент, крупный — несколько; дели по швам
   ответственности, не по числу файлов. Назначь порядок и способ обхода:
   независимые сегменты — параллельно; последовательно — лишь когда понимание
   раннего нужно для позднего (контракты ядра до адаптеров) или ради темпа
   расхода бюджета. Зафиксируй сегментацию и обоснование в `00-inventory.md`.

Пока субагент строит карту, не простаивай: разверни каркас пакета
`docs/audit/<дата>/` и нарежь срезы фактов по сегментам и линзам.

### 1. Аудит — `01-findings/`

Семь линз, **ортогональных по виду находок**. Делятся по тому, **что им нужно
видеть**:

- **Региональные** — судятся из самого сегмента: безопасность (десериализация
  артефактов, валидация входа на границе Reader), корректность (утечка таргета в
  CV и отборе признаков, детерминизм по сиду, метрики и их усреднение),
  производительность, чистота, локальная незавершённость (TODO/заглушки внутри
  сегмента). Аудитор читает вглубь один сегмент.
- **Сквозные** — нужен весь проект, дробление их слепит: архитектура и топология
  зависимостей (слои `.importlinter`, зависимости и extras), дублирование между
  сегментами, код↔документация (`docs/`, ADR, docstrings публичного API),
  глобальная незавершённость («определено, но нигде не потребляется» — мёртвые
  поля конфига, недостижимые пресеты и адаптеры). Аудитор проходит проект
  целиком — один раз, не на каждый сегмент.

**Региональные — по сегментам**, близкие линзы объединены в кластеры, чтобы не
плодить семь аудиторов на сегмент:

| Режим | Аудитор | Линзы (reference) |
|---|---|---|
| региональный, по сегментам | **Поведение** | безопасность (`security.md`) + корректность (`correctness.md`) |
| региональный, по сегментам | **Качество** | производительность (`performance.md`) + чистота (`cleanliness.md`) + незавершённость-локально (`completeness.md`) |
| сквозной, раз на проект | **Архитектура** | `architecture.md` |
| сквозной, раз на проект | **Гигиена между сегментами** | дублирование (`cleanliness.md`) + глобальная незавершённость (`completeness.md`) |
| сквозной, раз на проект | **Код↔документация** | `docs-conformance.md` |

Дефолт — два региональных аудитора на сегмент. **Дроби обратно**, когда
сегмент высокорисковый по одной линзе (leakage-критичный путь оценки или
десериализация артефактов из `profile.md` → корректность либо безопасность
отдельным аудитором); **объединяй**, когда сегмент крошечный.
Запускай сегменты по плану сегментации из фазы 0 (параллельно или по порядку);
сквозные аудиторы идут параллельно региональным.

Каждый аудитор — read-only, с чартером из четырёх частей (у субагента нет твоего
контекста, собери пакет сам):

- **Зачем:** что аудируется, для кого отчёт, что вердикт разблокирует —
  аудитор, знающий цель, ищет существенное, а не косметику.
- **Контекст-пакет:** карта из фазы 0 + **его scope** (региональному — границы
  сегмента: читать вне него ради прохода по вызову можно, но находки про свой
  сегмент; сквозному — весь универсум файлов) + срез фактов инструментов по его
  линзам + конвенции/прецеденты из `profile.md` + подавления из `learnings.md`.
- **Правила:** reference-файлы его линз (чек-лист + FP-контракт каждой), схема
  находки (ниже), лимит ~15 находок (выбирай самые существенные, остальное —
  одной строкой в разделе «за кадром»), запрет на правки и на бесцельные вызовы
  инструментов.
- **Выход:** структурированный список находок без прозы + обязательный вердикт
  `clean | issues | blocked` + статус `DONE | DONE_WITH_CONCERNS |
  NEEDS_CONTEXT | BLOCKED` — оркестратор обязан отличать «чисто» от «агент не
  смог проверить». `NEEDS_CONTEXT/BLOCKED` → дай недостающее и перезапусти, а не
  записывай в чистые.

### 2. Слияние и дедуп — начало `02-ledger.md`

Сведи находки всех аудиторов (региональных по сегментам и сквозных) в единый
реестр с ключом `file:line`. Заголовки находок не перефразируй — по ним работает
дедуп и сверка между фазами. Одно место, несколько источников (две линзы, два
сегмента, региональный + сквозной) → одна запись с пометкой всех источников.
Противоречия между линзами не разрешай молча — оставь рядом обе позиции с
нейтральной пометкой: решает пользователь.

### 3. Верификация — `02-ledger.md` (ядро)

По `../references/verification.md` (**читай перед фазой**). Коротко: каждый
Critical/High/Medium проверяет отдельный read-only верификатор, который
получает **только** находку (заголовок, file:line, цитата-доказательство,
сценарий) и контракт места — **никогда** рассуждения автора. Вердикты:
`CONFIRMED | TRADE-OFF | REJECTED(misread|noise)` с обоснованием. Отклонение с
причиной — успех верификатора, не неудача. Реестр держит три таблицы:
подтверждено / спорно / отклонено. Спорные на глубоком профиле уходят на
раунд скептиков. Находки без доказательства или сценария до верификатора не
доходят — возвращай автору (продолжи его через SendMessage — контекст находки
у него) или отбрасывай.

### 4. Отчёт — `03-summary.md`, `04-roadmap.md`

По `references/report.md` (**читай перед фазой**): сводка (executive-абзац,
вердикты и счётчики направлений, матрица severity × направление, «что солидно»,
приложение отклонённых с причинами), roadmap по effort-бакетам
(быстрые победы / средние / комплексные) с маршрутизацией: точечный баг →
`debugging-and-error-recovery`, системная перестройка →
`architecture-design`, недоспецифицированный функционал →
`spec-driven-development`. Каждый пункт сводки опирается на запись реестра
или вывод инструмента из этой сессии — пункт без свидетельства в отчёт не идёт.

### 5. Audit-gate — СТОП

Скил заканчивается отчётом. **Код здесь не правится** — аудитор, который сам
чинит, сам себе ставит оценку, и отчёт перестаёт быть независимым. Выведи
краткое резюме (общий вердикт, топ-находки, путь к пакету) и предложи
следующий шаг по roadmap. Фиксы — после явного решения пользователя,
соответствующим скилом.

## Повторный аудит

Если в `docs/audit/` есть прошлый пакет — это re-audit:

- **Сверка старых находок.** Каждую запись прошлого реестра проверь по
  текущему коду: исправлена / актуальна / устарела (код изменился — якорь
  `file:line` + цитата позволяет это определить). Динамику вынеси в сводку:
  закрыто N, осталось M, новых K.
- **Подавления.** Находки, отклонённые пользователем («это намеренно»),
  фиксируй в `learnings.md` (паттерн + scope + причина) — аудиторы следующих
  запусков загружают их и не флагают повторно.
- Сканируй с упором на изменённое с прошлого аудита (git history), но
  направления с плохой динамикой проходи целиком.

## Схема находки

Единая для всех фаз — без неё дедуп и верификация разваливаются:

```
[severity/confidence] Заголовок (стабильный, не перефразируется)
- Где: путь:строки
- Доказательство: дословная цитата кода (фальсифицируема верификатором)
- Сценарий: что и при каких условиях ломается/теряется (находка без
  внятного «почему это важно» автоматически понижается)
- Рекомендация: конкретный следующий шаг
- Fix-prompt: готовая инструкция для фикс-сессии (одна строка)
```

## Severity и уверенность — раздельные оси

| Severity | Семантика действия |
|---|---|
| Critical | блокирует релиз: нечестная метрика, утечка, сломанный публичный контракт — чинить немедленно |
| High | чинить до следующего релиза |
| Medium | в ближайший спринт |
| Low | при случае / при работе рядом |
| Info | к сведению, действие не требуется |

Уверенность — вторая ось, тремя уровнями: **подтверждено** (цитата и сценарий
воспроизводятся по коду), **вероятно** (механизм виден, но сценарию не хватает замера
или контекста), **гипотеза** (подозрение с планом проверки). Экспресс и стандартный
профили выдают только подтверждённое; «вероятно» — с явной пометкой, «гипотеза» —
на глубоком профиле и только с планом проверки. Severity без уверенности — приманка
для паники, уверенность без severity — шум.

## Делегирование субагентам

- **Глубина оркестрации = 1.** Оркестратор → аудиторы и верификаторы. Никаких
  координаторов-над-координаторами и агентов, запускающих агентов: каждый
  пересказ между уровнями теряет информацию и удваивает токены.
- **Сегментация — забота оркестратора.** Он один видит карту целиком, поэтому
  сам режет сегменты, назначает порядок и решает параллельно/последовательно;
  аудиторы получают готовый scope, а не выбирают его. Это не нарушает глубину 1:
  сегментацию делает оркестратор, а не агент-над-агентами.
- **Изоляция контекста.** Чартер собирается с нуля, история сессии не
  пересылается. Аудитор получает «зачем» и факты; верификатор — только находку
  и код.
- **Доработка цикла — продолжением того же агента** (SendMessage): автор
  находки доносит доказательство, верификатор перепроверяет после доработки.
  Свежий агент нужен там, где ценна непредвзятость, а не память.
- Пока аудиторы работают, оркестратор готовит каркасы отчётов и реестра.

## Reference-файлы

- `../references/lenses/<линза>.md` — чартер, чек-лист, FP-контракт линзы; общая
  библиотека, ею же ревьюит реализацию скил implementation. Передаётся аудитору,
  который её несёт (кластер — несколько файлов линз) — не читай все семь в
  основной контекст оркестратора.
- `../references/verification.md` — протокол верификации; общий с фазой Review
  скила implementation. **Читай перед фазой 3.**
- `references/report.md` — шаблоны сводки/roadmap, re-audit.
  **Читай перед фазой 4.**
